1. Executive Summary

What is PCORI SITL?

The PCORI Stakeholder-in-the-Loop (SITL) Dashboard is an interactive machine learning platform for healthcare researchers and clinicians to build, evaluate, and interpret predictive models for Opioid Use Disorder (OUD) and Overdose (OD) risk prediction.

The Problem

Healthcare ML models often fail in clinical practice due to:

  1. Black Box Problem: Clinicians cannot trust predictions they don't understand
  2. Data Disconnect: Models trained on data clinicians never see or verify
  3. Iteration Gap: Weeks to retrain models vs. minutes of clinician availability
  4. Deployment Barrier: Production ML requires specialized engineering skills

The Solution

PrincipleImplementation
TransparencyEvery prediction comes with SHAP feature explanations
InteractivityAdjust cohorts, retrain, see results in seconds
InterpretabilityAI-powered natural language explanations (GPT/Claude)
TrustValidate models against clinical intuition before deployment

3. Data Flow

Quick Training Pipeline

Open full-size diagram

Sequential Training Flow

  1. User selects parameters: T (sequence length), feature set, normalization
  2. API checks cache: If sequences are pre-computed, load from Parquet
  3. Chunked loading: Load 50k samples at a time (memory efficient)
  4. Train LSTM/GRU: PyTorch model with progress callbacks
  5. Return metrics: AUROC, loss curves, per-epoch progress

4. Data Model

Data Architecture Overview

The system is designed to work with any tabular patient data containing clinical features and a binary outcome. The data layer supports multiple data sources through a unified adapter pattern.

Supported Data Formats

Data SourceFormatUse Case
Development DataSQLiteRapid prototyping and UI testing with representative patient cohorts
Production EHR DataParquetLarge-scale Health Facts data with millions of patient records
Sequential DataNumPy arrays via Parquet cacheTime-series patient trajectories for LSTM/GRU models

Data Abstraction Layer

The system abstracts data access through configurable adapters, allowing the same UI and training pipelines to work with different underlying data sources:

Cohort Selection

Users define patient cohorts through intuitive filters. The system translates these into efficient database queries regardless of the underlying storage format.

Feature Engineering

Features are loaded dynamically based on the selected dataset. The adapter handles normalization, missing value imputation, and train/validation splits.

Sequential Data Pipeline

For temporal modeling, the system provides a high-level API that handles the complexity of loading and preprocessing sequential patient data:

# Load pre-processed sequential data
# Returns tensors ready for LSTM/GRU training

data = get_sequences(
    T=10,                      # Sequence length (time steps)
    feature_set="core",        # Feature subset to use
    normalization="standard",  # Data normalization method
)

# X_train shape: (N_patients, T_timesteps, D_features)
# y_train shape: (N_patients,) - binary outcome

Key Design Principle

The data model is intentionally feature-agnostic. The same infrastructure supports any clinical features relevant to the prediction task, whether demographic, diagnostic, procedural, or medication-based.

6. Data Loading

Pre-processed Data

Sequential EHR data is pre-processed into numpy arrays for efficient loading during training. The system loads data directly from pre-computed files:

Implementation

from backend.data_loader import get_health_facts_sequences

# Load pre-processed sequential data
data = get_health_facts_sequences(
    T=10,                      # Sequence length (time steps)
    feature_set="core",        # Feature subset
    normalization="standard",  # Normalization method
)

# Returns dict with numpy arrays:
# - X_train: (N, T, D) training sequences
# - y_train: (N,) training labels
# - X_val, y_val: validation data

9. Security Considerations

Current State (Prototype)

  • Simple username/password in code
  • Cookie sessions (30-day expiry)
  • Permissive CORS

Production Recommendations

  • Environment variables for secrets
  • Password hashing (bcrypt)
  • HTTPS + rate limiting
  • RBAC + audit logging
